# Rigorous Method Controller v2

Status: **working method, evidence-updated; not a claim of universal optimality**.

This file records how the method has changed during the Lean flywheel experiment while preserving the starting doctrine. The experiment ledger remains in `experiments/rigorous_lean_flywheel_v1.md`.

## 0. Where we started

The original working loop was:

`Residual → Obstruction → Representation/World portal → Certificate → Lawbook → sharpen residual`.

The original controller discipline was:
- external verifiers decide hard claims;
- proposals, heuristics, routing, memory policy, and representations remain revisable;
- distinguish search failure from representation/operator/specification/applicability failure;
- retain only scoped, verifier-backed capability;
- compile stable repeated cognition into cheaper deterministic machinery;
- optimize long-run solver state, not only the current answer.

Nothing below replaces that foundation. The changes below refine **when** to broaden, **how** to use failure, and **when** to step back and compress several local solutions into one reusable capability.

## 1. Main correction earned by the flywheel run

Do **not** default from failure to broader search or a richer representation.

Default transition:

`FAILURE → SPLIT THE RESIDUAL → SEPARATE RIVAL CAUSES → RUN THE SMALLEST DECIDING TEST`.

Only broaden when the surviving residual demonstrates that the current representation/action language cannot express the needed distinction.

This prevents capability explosion and makes negative results productive.

## 2. Updated inner loop: differentiate before expanding

For a live residual `R`:

1. **FREEZE**
   - freeze the claim, environment, verifier, budget, and currently admitted capability state;
   - distinguish infrastructure negatives from semantic negatives.

2. **SPLIT**
   - factor `R` into mutually discriminating candidate causes where possible;
   - examples: search incomplete / representation missing / information unavailable / operator absent / applicability error / proof-object extraction / interface totalization / verifier limitation.

3. **SEPARATE**
   - choose the smallest experiment whose result eliminates or sharply demotes at least one branch;
   - prefer high residual-space reduction per unit cost over raw experiment count.

4. **PRUNE / SHARPEN**
   - retain failed hypotheses as killed branches, not forgotten attempts;
   - rename the surviving residual at the most precise earned level.

5. **BROaden only if licensed**
   - add a representation/operator/observable only when the sharpened residual specifically licenses that intervention;
   - otherwise continue decomposition/search inside the current language.

6. **SOLVE THE SHARP RESIDUAL**
   - construct the smallest intervention that should close the surviving obstruction.

7. **VERIFY / ABLATE / SCOPE**
   - external verifier first;
   - test rivals, minimality/causality, protected purpose, transfer, and applicability boundary where relevant.

8. **RETAIN OR REJECT**
   - admitted capability enters persistent solver state;
   - failed stronger claims remain explicit negative capital.

## 3. Periodic outer loop: zoom out and join the dots

Local solving must be interrupted periodically by a deliberate **SYNTHESIS REVIEW**.

Trigger a synthesis review when any of the following occurs:
- 3 or more verified solutions use visibly similar mechanisms;
- several residual splits converge on one repeated boundary;
- the same proof/search cost is paid independently more than once;
- one capability produces multiple downstream adapters;
- the current residual vocabulary has become much finer than the vocabulary at the previous review;
- experiment throughput is high but frontier movement is low;
- the user explicitly asks to step back / join the dots.

During synthesis review:

1. collect the last verified positive and negative episodes;
2. ignore superficial source similarity; group by causal role/invariant/obstruction;
3. ask whether several solutions are instances of one constructor, normalizer, quotient, routing rule, applicability law, or representation change;
4. formulate the smallest reusable abstraction `K`;
5. test whether `K` reproduces the known instances;
6. test `K` on a source-distinct case;
7. ablate `K` or compare against a cold route;
8. install `K` only if the abstraction changes future search cost/frontier rather than merely shortening code.

This is the **UPWARD** motion of the method.

## 4. The two motions

The controller now explicitly alternates:

### DOWN: residual differentiation
`R → {R1, R2, ...} → smallest surviving obstruction`.

Purpose: increase explanatory resolution and eliminate false mechanisms.

### UP: verified compression
`{S1, S2, ...} → K`.

Purpose: reduce future descriptive/search complexity by compiling repeated verified structure.

Too much DOWN produces endless special cases.
Too much UP produces premature generalization.
The verifier regulates both.

## 5. Search should leave capital

Each episode has two outputs:

- **production output:** the current verified solution/certificate;
- **capital output:** any verified change to the future solver—law, obstruction, constructor, normalizer, representation, applicability boundary, killed rival, index/cache/compiler, or routing rule.

A search episode is unusually valuable when either PASS or FAIL removes a large region of future residual space.

Working objective:

`maximize verified future residual-space eliminated + verified productive capability gained, per unit of evidence/search cost`.

Do not optimize solve count alone.

## 6. Negative results are first-class capital

A verifier rejection should, where possible, produce one of:
- killed mechanism;
- narrower scope;
- named logical/representation boundary;
- distinction between Prop-level existence and Type-valued computational data;
- infrastructure residual;
- evidence that an abstraction was premature.

Never silently replace a rejected strong claim with a weaker success. Preserve the rejection and record exactly what survived.

The Lean sequence O5/O8/O12/O17 is the canonical example for this controller version.

## 7. Current example of periodic compression

The quotient-completeness line started from a broad residual:

`Completeness uses Classical.choice`.

Residual splitting progressively separated:
- finite observable support;
- local representative existence;
- repeated-variable coherence;
- totalization/support retraction;
- Prop existence versus Type-valued data;
- computational support indexing;
- arbitrary family choice versus special quotient structure.

The periodic zoom-out then joined empty/left/right quotient sections into the normalizer abstraction:

`normalizer + derivability invariance + derivable reduction → constructive quotient section`.

O29 compiled that abstraction; O30 subsequently transferred it to associativity, a non-collapsing quotient. This is the model for future synthesis reviews.

## 8. Method-on-method review

The method itself is a valid residual-bearing object.

Every synthesis review should include a brief controller audit:
- Which controller decision caused wasted search?
- Which split produced the most information?
- Did we broaden too early?
- Did we overfit an abstraction?
- Did a negative result reveal a missing residual category?
- Did accumulated capability improve the next residual decomposition?
- What repeated manual controller action can now be compiled?

Controller changes must obey the same discipline:
`proposal → frozen comparison → intervention → verifier/evidence → ablation where possible → retain/reject`.

Do not rewrite history. Append method versions and state why each change was earned.

## 9. Compounding criterion remains strict

Do not call repeated reuse "compounding" merely because code/proofs get shorter.

Strong target:
- admitted capability `O1` causally changes discovery/acquisition of later `O2` under matched conditions;
- later accumulated state improves subsequent residual decomposition or capability acquisition;
- ablation of the prior capital removes that advantage;
- ideally the return on the next unit of verified search improves with accumulated capital.

The current Lean work shows verified transfer, compression, sharpened residual ontology, and reusable normalizer compilation. It does **not yet** establish open-ended compounding.

## 10. Current compact controller

`FREEZE → SPLIT → SEPARATE → PRUNE → SHARPEN → [BROADEN only if licensed] → SOLVE → VERIFY → RETAIN → REPLAY`

Periodically:

`ZOOM OUT → JOIN VERIFIED DOTS → COMPRESS → TRANSFER TEST → ABLATE → COMPILE → UPDATE RESIDUAL ONTOLOGY → CONTINUE`.

And periodically on the controller itself:

`REVIEW METHOD AGAINST OBSERVED RETURNS → VERSION, DON'T ERASE`.

Review this controller again after either:
